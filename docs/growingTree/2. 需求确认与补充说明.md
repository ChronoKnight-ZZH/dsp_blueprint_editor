## 3. 三处与项目现状冲突的地方（均已收敛）

### 3.1 时序：5 秒是"下限"——那它和 252 个动作放在一起会怎样？

**已确认口径**（你的答复）：后端生成速度不固定；**若事件流在 5s 内输出完，动画最短 5s**；后端更慢时动画跟随流，不追求 5s。

把它写成两条不变量：

1. `T_total ≥ 5s`（当 `stream_cost ≤ 5s`）——**5 秒是地板，不是天花板**；
2. 队列空才 commit；后端慢 ⇒ 队列几乎不积压 ⇒ 总时长 ≈ 后端耗时 + 尾部（≤ 一个 T）。

地板本身不冲突，**冲突发生在地板与样例规模相遇时**：252 个动作 × T=200ms = **50.4s**，它满足"≥5s"，但比"约 5 秒量级"长 10 倍。也就是说，只靠"下限"约束无法决定 T，还必须回答"每步该多慢"。

数学边界：`n` 个串行动作想摊进 5s ⇒ 每步 5s/n。样例 n=252 ⇒ **每步 ≈ 20ms ≈ 1.2 帧 @60Hz**。所以：

> **"每一步都看得清"（T≈150~200ms）与"总时长 5s"在 n>25 时数学上不可兼得。** 必须选一种取舍。

| 落法 | 规则 | 样例总时长 | 代价 |
| --- | --- | --- | --- |
| A. 固定 T=200ms（下限只做校验） | 总时长 = n×T，若 <5s 则整体拉伸 | **50.4s** | 满足"看得清"，但流程长、用户等 |
| B. 固定预算 5s | T = 5000/n（下限 40ms 兜底） | 5.0s | 铺开快、**每步糊**，与"基础时长内看清细节"相悖 |
| C. **对齐 5s 地板 + 自适应追赶（推荐）** | ①`T_eff = clamp((5000 - elapsed)/pending, 40ms, 200ms)`，动作内冻结；②队列空但 `elapsed < 5s` 时**终态停留**到 5s 再 commit | 快流 ≈ 5s；慢流 = 流耗时 + 尾部 | 复杂度 +20 行；commit 时刻从"队列空"变成"队列空 **且** 满 5s" |
| D. 按动作规模分档 | 小动作（≤8 操作）200ms；大动作（≥30）压缩到 60~80ms | 约 8~12s | 时长不可预测，用户体验不齐 |

C 的效果：开始时 `pending≈252` ⇒ T≈20ms，把大批量铺开；随着队列缩短，T 自动回到 200ms，**最后十几个动作是"慢动作"**，用户能看清终局细节。且当 `stream_cost > 5s` 时 `pending` 恒小 ⇒ 公式自动退化成 T=200ms，即"跟随事件流"，与你确认的口径完全一致。

> C 必须带②那半条：只做①的话，若后端 3s 发完且队列恰好排空，总时长仍是 3.2s，**照样违反"最短 5s"**。这半条会带来一个连带影响需要你确认：**commit（硬切正式结果）的时刻变成 `max(队列排空, 首事件 + 5s)`**，即"后端已完成"与"用户看到终态"最多差几秒 → 界面上"生成完成"与"动画播完"最好分开显示，否则会被当成卡死。

两点实现约定（避免踩自己的坑）：
- **T 只在动作开始时取一次，动作内冻结**——否则"同动作内起止帧一致"这条不变量会被打破；
- 正弦 LUT **按相位 0~1 归一化**（256 点固定表），与 T 解耦，T 变化不必重建 LUT。

> **已选：C（Q1'）**。落地时要同时实现①自适应 T 与②终态停留对齐 5s，缺①会拖成 50s，缺②会在快流下退化成 3 秒闪现。另外请尽量补一个实测值：**这 252 条 delta 从第一条到 `preview-complete` 的墙钟耗时**——它决定 `pending` 曲线是否真的会触发追赶（若实测本来就 >5s，那 C 会自动退化为 A，代码照写不误）。

### 3.2 构建工具：本仓库没有 Vite，`import.meta.env` 在当前配置下**会直接编译失败**

- 本项目是 `vue-cli-service build`（webpack 5），`import.meta.env` 是 Vite 的约定，webpack 不认；
- 更硬的约束：库里 **UMD 产物不允许出现 `import.meta`**，项目已经踩过并写在注释里（`src/lib/assets/assetBaseUrl.ts:24-28`：`DefinePlugin` 注入 `import.meta.url`，UMD 注入 `undefined`）；
- 结论：**"在代码里写 `import.meta.env.VITE_xxx`"这一条，在本仓库要么改构建工具，要么换等价写法**。等价写法见 §4.2，收益/成本几乎一样（都是构建期常量 + 死代码剔除），且不需要迁移。

（若你确实打算迁 Vite，那是**独立的一期工程**：`vue-cli-service` → Vite、`scripts/lib-build/build.js` 的 webpack API 全部重写、`require.context` 资产解析层重写、PWA/Workbox 换插件、Pages 部署脚本改。不建议和动画功能同批做。）

### 3.3 "多模式"到底切什么：三个概念被混在一起了（已按 Q3 结论收敛）

方案里"低/中/高模式"指的是**并发上限**（调参），而你现在提的"多模式构建"指的是**构建期裁剪**（体积/功能开关）。两者目的不同、实现不同、也不该绑死：

| 维度 | 想解决的问题 | 正确形态 | 错误形态 |
| --- | --- | --- | --- |
| 功能开关（构建期） | 包体积、宿主是否带动画 | 常量 + 死代码剔除，**整模块不进产物** | 用运行时 if 判断（体积不减） |
| 并发上限（运行期） | 低端机帧率 | 运行时配置对象（像现有 `ViewerRenderSettings`） | 写进构建期模式（改个数字要重新构建） |
| 设备降级（运行期） | 未知设备能力 | 运行期探测 + 自动降档 | 让用户自己选构建版本 |

> **已定（Q3）**：构建期只切"有没有动画层"这一刀（`off` / `on`）；`T` 与并发上限走运行时配置。理由：动画层预估 15~30KB（gzip），切成 3 个构建版本的收益递减，而 3 份回归 + 3 份 CI + 3 套 SW 缓存是线性上升的成本。

## 4. 「多模式构建」可执行口径（推荐方案）

### 4.1 模式矩阵（已定：2 档构建 × 运行期参数）

| 构建模式 | 含义 | 产物 | 谁用 |
| --- | --- | --- | --- |
| `off` | 预览增量**直接应用**（或忽略中间态，等 commit 一次成图），动画层代码**完全不在产物里** | `dist-off/` | 宿主 Wails 桌面版（包体敏感）/ 低端设备 |
| `on` | 完整动画层（含移动双副本、LUT、调度器） | `dist/`（保持现状，Pages 继续发这一份） | Web 演示页、正常设备 |

运行期参数（两种构建都保留，仅 `on` 构建生效）：`T`（默认 200ms，下限/上限可配）、`maxConcurrentMove`、`maxConcurrentRemove/Add`、`backlogLimit`。

### 4.2 实现骨架（webpack 等价于 Vite 的 `import.meta.env`）

**① 唯一读取点**（以后迁 Vite 只改这一个文件，全项目不感知）：

```ts
// src/config/featureFlags.ts —— 全项目唯一读构建期开关的地方
/** 由 vue.config.js / scripts/lib-build/build.js 的 DefinePlugin 注入；
 *  off/on 用独立布尔常量，避免 'false' 字符串为真的坑。 */
declare const __DSP_ANIM_ON__: boolean;
export const ANIM_ON: boolean = __DSP_ANIM_ON__;
```

**② 构建期注入**（`vue.config.js` 与 `scripts/lib-build/build.js` 各加一行，读 `DSP_ANIM` 环境变量并做白名单校验）：

```js
// 只接受 on/off，其它值直接让构建失败（避免拼错后静默降级）
const ANIM = (() => { const v = (process.env.DSP_ANIM ?? 'on').toLowerCase();
  if (v !== 'on' && v !== 'off') throw new Error(`DSP_ANIM 只能是 on/off，收到: ${v}`);
  return v === 'on'; })();
// plugins: new webpack.DefinePlugin({ __DSP_ANIM_ON__: JSON.stringify(ANIM) })
```

**③ 整模块剔除**（关键，照抄项目已有的 `@lib/asset-resolver$` 范式）：

```
src/preview/layer.ts      ← 唯一 import 点：export * from '@preview/impl'
src/preview/impl.on.ts    ← 真正实现（调度器/槽/shader 注入/动画）
src/preview/impl.off.ts   ← 空实现，接口签名完全一致（直接应用 + 无动画）
```

```js
// vue.config.js 内，与现有 alias 并列
resolve: { alias: { '@preview/impl$': path.resolve(__dirname,
  ANIM ? 'src/preview/impl.on.ts' : 'src/preview/impl.off.ts') } }
```

> 为什么不用"常量 + `if`"？静态 `import` 会被提升、无条件进模块图，`if(false)` 只能靠 terser 事后删，**不能保证三方依赖（shader 注入那套）也消失**；别名切换是"文件根本不存在"，体积有物理保证。
> 代价：TS/Jest 需要一条 `paths` 或声明文件对齐（项目已有 `tsconfig` 与 `jest.config.js`，加一处即可）。

**④ 用法**：

```bash
yarn build       # 默认 on（= DSP_ANIM=on vue-cli-service build --dest dist）—— 保持现有 CI/Pages 不变
yarn build:off   # = DSP_ANIM=off vue-cli-service build --dest dist-off
yarn build:lib   # 库：scripts/lib-build/build.js 读同一个 DSP_ANIM，产出 on 版
yarn build:lib:off
```

> 环境变量走**构建脚本**而不是 `.env` 文件，理由：`.env` 只能给 `VUE_APP_*` 且值一律是字符串（`'false'` 为真），而且 on/off 是"发行形态"不是"环境"，用命令行更明确。若你要 IDE 内切换，再加 `.env.off/.env.on + --mode` 也行（Vue CLI 5 支持），但两套入口别并存。

### 4.3 体积验收（写进 CI，防回退）

1. 分别构建 on/off，记录 `dist*/js/*.js` 的 gzip 体积；
2. **断言**：off 产物中 grep 不到动画层标记字符串（如 `aOpacity`、`__DSP_ANIM_SENTINEL__`）；
3. **断言**：`size(on) - size(off) >= 预算`（预算等实测后填，先按 ≥ 10KB gzip 记）；
4. CI 现只发一份 `dist`（`.github/workflows/gh-pages.yml`）：**结论：Pages 仍只发 on 版**，off 版只作为宿主依赖/内部产物（否则还要处理两套 SW 缓存作用域）。若以后要发两套，publicPath 必须分开（`/dsp_blueprint_editor/off/`），否则 `service-worker.js` 与 precache 会互相覆盖。

### 4.4 库（`dist-lib`）双形态（已定：Q4 = 双形态）

宿主是 Wails 桌面应用，包体敏感 ⇒ 库必须给宿主一个"无动画"选择，不能替它决定。

**产物矩阵**（4 个 JS + 2 份 d.ts，构建脚本各跑两轮）：

| 产物 | 说明 |
| --- | --- |
| `dsp-blueprint-editor.umd.js` / `.esm.js` | on 版（现状不变，`main`/`module` 仍指它们） |
| `dsp-blueprint-editor.lite.umd.js` / `.lite.esm.js` | off 版（无动画层），供包体敏感宿主 |

```jsonc
// package.json 增量（保持 main/module 向后兼容，新增 subpath）
"exports": {
  ".":       { "types": "./dist-lib/index.d.ts", "import": "./dist-lib/dsp-blueprint-editor.esm.js", "require": "./dist-lib/dsp-blueprint-editor.umd.js" },
  "./lite":  { "types": "./dist-lib/index.lite.d.ts", "import": "./dist-lib/dsp-blueprint-editor.lite.esm.js", "require": "./dist-lib/dsp-blueprint-editor.lite.umd.js" }
}
```

> 注意两点：① 现在 `package.json` 的 `files` 只有 `dist-lib`，加产物不用改；但 `build:lib` 脚本目前是"两个 target 各编译一次"，加 lite 后变 **2×2=4 次编译**，CI 时长翻倍，需要确认可接受（或只在 release 时构建 lite）。② 两个形态的**类型声明必须同签名**（`impl.off.ts` 与 `impl.on.ts` 共用 `.d.ts`），否则宿主 TS 项目换个入口就编译不过。

## 5. 方案没写透、但会直接踩坑的 7 个实现细节（补充说明）

### 5.1 `InstancedMesh` 的 `count` 是构造期写死的
`glbInstances.ts:79` 与 `buildBuildings.ts:105/127/172` 都按**精确数量**分配。增量 `add` 意味着要么
(a) 预分配 headroom（如 `ceil(count × 1.35) + 16`，空闲槽 `aOpacity=0` 且矩阵写到远处），要么
(b) 动画对象放在**独立预览层**（自己的 InstancedMesh，容量独立），播完 commit 时与正式层对齐。
建议 (a) 作为主路（不增 draw call），(b) 作为 off 模式/极端规模兜底。**代价：`instanceMatrix`/`instanceColor` 缓冲会变大，需实测显存与上传耗时。**

### 5.2 `aOpacity` 注入会污染共享材质，而且会被二次重贴图冲掉
- GLB 材质来自缓存、被多个 `InstancedMesh` 共用（`glbInstances.ts:80-81` 明确"共享资源"）；对材质做 `onBeforeCompile` 会一次性影响所有使用者。若某处用了**非实例化** `Mesh` 跑同一材质（如 `src/blueprint/reform.ts:261` 的板），几何里没有 `aOpacity` 属性 → 轻则报错、重则该 mesh 消失。
- `reapplyLoadedModelMaterials()`（`glbLoader.ts:356`）在设置变更时会**重新贴图**，会重新编译材质 → 注入必须幂等，并且设定 `material.customProgramCacheKey`，否则 shader 程序会被反复重建（编译卡顿正是"跳帧"的主要来源）。
- 建议：**只在预览层专用的材质克隆上注入**（`material.clone()` + `customProgramCacheKey = 'aopacity-v1'`），或者给几何体补一个默认 `aOpacity=1` 的 attribute 做兜底。**这条要和"不替换现有架构"一起权衡，必须验证。**

### 5.3 `onTick` 要挂两处，且两处循环的语义不同
编辑器循环在退出时靠 `mounted` 标志停（`BlueprintEditor.vue:464-471`），库循环靠 `disposed`（`RenderCore.ts:891-894`）。`onTick` 注册表要能**按 owner 注销**，否则切换蓝图/销毁后仍有回调在跑 → 内存泄漏 + 幽灵动画。

### 5.4 BVH 是"整场景重建"的一部分，不能在动画期间每帧重建
`buildBVH`（`src/lib/core/buildBuildings.ts` 调用链）为全场景建加速结构；490 个对象每帧增删都重建的话必然掉帧。方案里"动画期间拾取用逻辑位置"等于**用静态 BVH 打动态物体**，点击会点空。**建议：预览期间禁用拾取/悬停信息**（用户此时只是在看生成过程），比"对齐 BVH"便宜一个数量级。

### 5.5 off 模式的语义必须写死，否则是最隐蔽的 bug 源
`off` 构建里所有动画分支被剔除后，仍要保证：delta 到达 → 直接 `applyDelta`（或忽略）→ `commit` 成图；且**不能有任何代码路径试图调用动画层 API**。建议 `impl.off.ts` 实现"直通 + 无动画"，并加一条单元测试：off 模式下 `enqueue()` 立即生效、队列恒空。

### 5.6 数据侧的两个语义要确认
- **移动判定**：`replace` 中坐标/朝向变化才算移动，阈值多少？（样例有 192 次 replace 位置不变——大概是参数/配方变化，应当**只更新不播位移动画**，否则会看到"原地抖动"）；
- **同对象连续 replace**（样例 72 次 `replace→replace`）：方案说"同对象不合并、逐条播"，那一个对象会被连续淡入淡出两次；需要确认这是期望效果（我认为是，但要有心理预期）。

### 5.7 库要新增公开 API（Q4 定了双形态，这条就绕不开）
`BlueprintViewer` 目前只有全量加载（`loadBlueprint*`），**没有增量入口**（`src/lib/BlueprintViewer.ts:212-239`）。预览流要走库，公开面至少需要：

```ts
/** 追加一条预览增量（内部按 sequence 保序、排队播） */
applyPreviewDelta(delta: PreviewDelta): void;
/** 预览结束：标记不再有新事件，队列播完才 commit */
completePreview(): void;
/** 放弃本次预览（失败/abort）：按 Q10 的策略收尾 */
discardPreview(): void;
```

对应成本：`src/lib/index.ts` 的导出面 + `scripts/lib-build/index.d.ts` 手写类型 + `lib-README.md` 文档三处都要同步；且 **off 版这三个方法必须存在**（空实现），否则宿主同一份调用代码换个入口就 `undefined is not a function`。

## 6. 问题清单

标注：**P0 = 不答就不能开工**；P1 = 影响设计与验收；P2 = 可后补。

**已全部关闭**：Q1（5s 是下限，落法选 C）、Q2（webpack 等价实现）、Q3（两档 + 运行时调参）、Q4（库双形态）、Q1'（自适应追赶 + 终态停留）。

> 也就是说：**当前没有阻塞开工的问题**。下面 P1/P2 可以在第一版原型跑通后再逐条确认。

**P1**
- **Q5（实测）**：能否提供一次真实生成的**事件到达时间线**（每条 delta 的时间戳）与一次**基线帧率**（目标设备）？前者定时序，后者定"90% 基线"的分母。
- **Q6（卡顿口径）**："无 > 2 帧卡顿"按 60Hz 即"相邻帧间隔 > 33ms 记一次"，是否认可？另外是否要一个绝对下限（如 ≥ 45fps）？
- **Q7（动作结束条件）**：动作的"结束"是"该动作所有槽都跑完 T"还是"T 到点即结束"（含被后续同对象操作覆盖的情况）？后者会导致"看起来没播完就切下一个"。
- **Q8（拾取）**：预览期间**禁用拾取**是否可接受（推荐）？若必须可拾取，接受"点到的位置是静态位置"的误差吗？
- **Q9（容量）**：是否接受为增量增删**预分配 headroom**（§5.1）？峰值 490 对象、单动作 128 操作，可以按 `实际数 × 1.35 + 16` 起标定吗？
- **Q10（异常收尾）**：生成失败/abort 时，正在播的动画是**立即清空硬切**（推荐，快）还是播完再丢弃？
- **Q11（off 模式行为）**：off 版在 delta 到达时是"立刻应用（用户会看到一段段跳变）"还是"完全忽略、只等 commit 一次成图"（更省、但也更"黑屏一段时间"）？
- **Q15（库构建成本）**：`build:lib` 从 2 次编译变 4 次（on/lite × ESM/UMD），CI 时长翻倍。可以接受吗？还是 lite 只在 release 时构建？

**P2**
- **Q12（命名/入口）**：`DSP_ANIM=on|off`、`build:off` / `build:lib:off` 这套命名是否接受？
- **Q13（验证页形态）**：验证页是否要在同一个页面里**切换模式**（顺带验证多模式构建）？放在 `public/verify/preview.html` 还是 `demo/`？
- **Q14（移动阈值）**：`replace` 位置变化多少算"移动"（如 > 0.01 格 / > 1° 朝向）？参数变化类 replace 只更新不播动画，对吧？
