## 1. 需求理解摘要

1. **目标**：为 Three.js 增量预览事件（`add`/`remove`/`replace`）实现一个流式动画渲染层，让模型变化“丝滑、行云流水”，单步变化在基础时长 T 内可看清细节，完整动画约 5 秒量级（理想值，不硬约束）。
2. **关键约束**：保持现有 InstancedMesh 合批 + BVH 拾取架构；严格按 `sequence` 流式逐条播放、**不丢任何动画、同对象不合并**；**动作内并发、动作间串行**（一条事件=一个动作）；动作内按操作类型设并发上限（移动低、删除/新增可全量）；移动用双副本交叉淡化（原位置淡出 + 新位置淡入，同时起止）；正弦曲线节奏；正弦缓动与动画层从零自研；**队列全部播完后硬切正式结果**。
3. **成功标准与优先级**：帧率稳定、无跳帧 > 动画完整性 > 总时长。500ms 级单步内主线程不被长任务阻塞，是验收的第一口径。

------

## 2. 完整可执行方案

### 2.1 目标

- **总体目标**：交付一个可挂接到 `generateFactory` 事件流上的预览动画渲染器，输入 `preview-delta`，输出逐条、可看清、不掉帧的变化动画，播完硬切正式结果。
- **可量化成功标准**（阈值待实测标定，先给口径）：
  - 单步动画期间帧率不低于场景基线帧率的 90%，无 > 2 帧的卡顿；
  - 同一动作内所有操作**起止帧一致**（交叉淡化两边同时开始、同时结束）；
  - 事件应用顺序与 `sequence` 严格一致，无乱序、无丢操作；
  - 队列播完到硬切的判定准确（以队列空为准，不以计时为准）。
- **验收口径**：用下面的“可验证文件”跑顺序断言 + 帧率采样 + 起止帧断言。

### 2.2 技术栈

- **渲染**：现有 Three.js + InstancedMesh 合批（沿用，不替换）。
- **per-instance 透明度**：`InstancedBufferAttribute`（每个槽的 `aOpacity`）+ `onBeforeCompile` 注入片元透明度；双副本 = 同一逻辑对象占用两个槽，各自独立 `aOpacity`。**选型理由**：draw call 不增，是唯一能扛住高规模并发的路线。
- **实例槽分配器**：`objectId → 逻辑对象 → 1~2 个物理槽`；槽池复用，动画结束释放多余槽。**这是 A 方案的关键配套**。
- **补间/驱动层**：自研极简层，不引入 GSAP/tween.js。**理由**：只需正弦缓动 + 透明度/位置/姿态插值 + 每帧 tick，自研约百行，能直接写 instance attribute，避免库与 InstancedMesh 的适配成本和额外抽象。
- **正弦缓动**：`ease(t) = 0.5 - 0.5*cos(πt)`，预计算为采样表（LUT），每帧查表，避免逐帧三角函数。
- **每帧钩子**：在现有 rAF 主循环里加一个 `onTick(cb)` 注册表，调度器注册一个 tick，集中更新所有在播动画的槽属性。
- **多线程判断**：**不引入 Web Worker**。你的真实目标是“主线程不卡”，而方案里每帧只做“查表 + 写少量 instanced attribute”，计算量极轻；Worker 的通信与同步开销反而可能引入抖动。预计算 LUT 已把重计算移出每帧。若后续实测主线程仍有其他重活，再按备选方案 2 引入。
- **测试**：自包含验证页（见 2.5）。

### 2.3 执行方案要点

**阶段一：准备与基线**

- 做什么：在 rAF 主循环加 `onTick` 注册表；盘点材质清单（哪些材质会被注入 shader）；用现有场景测基线帧率。
- 产出物：`onTick` 钩子、材质清单、基线帧率记录。
- 依赖/风险：`onBeforeCompile` 注入要与现有材质/后处理兼容，先做最小注入回归。

**阶段二：渲染层（A 方案落地）**

- 做什么：实现槽分配器（逻辑对象 ↔ 物理槽，1~2 槽）；实现 per-instance `aOpacity` shader 注入；实现槽的矩阵/透明度写入接口。
- 关键要点：跨模型类型的 `replace` **退化为删除+新增**（避免跨 InstancedMesh 双副本）；动画期间 BVH 拾取用**逻辑对象位置**或暂停拾取，避免与物理槽位置不一致。
- 产出物：槽分配器、注入后的材质、拾取兼容说明。
- 风险：shader 注入回归面广，需逐材质验证。

**阶段三：调度层**

- 做什么：动作队列（按 `sequence` 保序、忽略重复/旧序号）；动作内按类型分桶并施加并发上限（移动低、删除/新增全量）；同对象串行状态机（`objectId` 在播时，后续操作排队）。
- 关键要点：一个动作 = 一条事件，动作内所有操作共享同一 T 起止；动作间严格串行；队列空才允许硬切。
- 产出物：调度器、并发上限配置（低/中/高模式）。
- 风险：严格排队导致延迟累积，需在 UI 上给“动画播放中”状态，避免用户误判卡死。

**阶段四：动画层**

- 做什么：正弦 LUT；属性驱动（透明度、位置、姿态）；交叉淡化 = 原槽 `aOpacity 1→0`、新槽 `0→1`，同一 T 内互补；删除 = 单槽 `1→0` 后释放；新增 = 单槽 `0→1`。
- 关键要点：起止帧对齐用“动作开始帧 + LUT 索引”统一驱动，保证同动作内所有操作同时开始、同时结束。
- 产出物：动画驱动模块。
- 风险：半透明叠加可能发灰，需按材质确认混合模式。

**阶段五：集成**

- 做什么：`onProgress` 里 `preview-delta` → `applyDelta` 入队；`preview-complete` 只标记；`generateFactory` 成功返回后，**等队列播空**再 `commit` 硬切正式结果；失败/abort 走 `discard`。
- 关键要点：`sequence` 过滤放在入队前；渲染异常在预览模块内部吞掉，不向回调外抛。
- 产出物：`useBlueprintPreview` 对接层（按文档第 6 节结构扩展）。

**阶段六：测试与调优**

- 做什么：用验证页跑顺序/起止帧/帧率断言；实测标定 T 与各模式并发上限；压测峰值规模。
- 产出物：标定后的配置表、验收记录。

### 2.4 结果

- **功能结果**：事件流逐条播放，同对象逐条不合并；动作内并发、动作间串行；移动双副本交叉淡化同时起止；删除淡出、新增淡入；队列播完硬切正式结果。
- **性能/质量指标**：单步动画期间帧率 ≥ 基线 90%，无 > 2 帧卡顿；顺序零错乱；起止帧一致。
- **交付物清单**：`onTick` 钩子、槽分配器、shader 注入、调度器、动画驱动、对接层、验证页、标定配置。
- **验收方式**：2.5 的验证页断言 + 真实事件流回放。

## 3. 备选方案（最多 2 个）

**备选 1：动画对象摘出为独立 Mesh（B 方案）**

- 一句话：参与动画的对象临时从 InstancedMesh 摘出、独立播完再合并回。
- 重点：绕开 per-instance 透明度；动画期 draw call 增加；与 BVH 同步复杂。
- 适用：模型类型少、单动作操作数低、shader 维护成本不可接受时。
- 主要风险：高规模并发时帧率不稳。

**备选 2：Worker + OffscreenCanvas 渲染卸载**

- 一句话：把渲染循环整体移入 Worker。
- 重点：主线程几乎不参与渲染；对 Three.js 版本/材质/后处理要求高；改造量大。
- 适用：主线程还有大量非渲染重活、A 方案仍被主线程其他任务拖累时。
- 主要风险：兼容性与改造周期。

------

## 4. 关键风险与取舍

- **双副本槽管理复杂度**：取舍是“逻辑对象与物理槽分离 + 跨类型 replace 退化为删除+新增”，牺牲少量跨类型移动的连续性，换取槽管理可控。
- **严格排队导致延迟累积**：你已选择接受，5 秒不硬性；取舍是 UI 上必须显示“动画播放中”，否则用户会误判卡死。
- **BVH 拾取与动画位置不一致**：取舍是动画期间拾取用逻辑位置或暂停，保证不误拾取。
- **shader 注入回归面**：取舍是先做最小注入 + 逐材质回归，避免一次性改太多。
- **硬切收尾的视觉断裂**：你已明确以“队列播完”为触发，接受这次硬切，换取动画完整性。
