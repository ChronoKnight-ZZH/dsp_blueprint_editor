## 1 需求

在 `BlueprintViewer`（lib 发布层）新增**纯 API** 删除能力，由 MES和UMD 端调用，不涉及 3D 交互、UI 与撤销栈。

| 编号 | 需求                                                         | 来源                      |
| ---- | ------------------------------------------------------------ | ------------------------- |
| R1   | 入口为**一个方法** `deleteBuilding(mode, targets)`，第一参数 `mode` 取 `0/1` | 用户本轮                  |
| R2   | `mode=0`：按 itemId 删除**全部同类建筑**                     | 用户本轮                  |
| R3   | `mode=1`：按**建筑 ID**（`BlueprintBuilding.index`）数组删除**指定建筑组** | 用户本轮                  |
| R4   | 第二参数为数组，**长度不限、不得为空**                       | 用户本轮                  |
| R5   | 任一目标不存在 → **整批失败**，原数据不变                    | 用户本轮                  |
| R6   | 复用现成删除命令，不新写删除算法                             | 用户首轮 + CODE_WIKI §6.4 |
| R7   | 失败不抛异常，返回统一 `{ ok, value } \| { ok, error }`      | lib-README §5.4           |

> **R5 的落笔口径（rev.2 定案）**：`mode=0` 时"目标不存在"= 某个 itemId **一栋都没命中**；`mode=1` 时 = 某个建筑 ID 在 `data.buildings` 里找不到。两种模式**一律整批失败**，不做部分删除。这样 `removed` 恒 ≥ 1，返回值不需要承载"部分成功"，也为将来加 `unknownIds` 预留了空间（见 §6.6）。
>
> R2/R3 的 0/1 映射按「0=itemId、1=建筑 ID」落笔（与"第一种…第二种…"的叙述顺序一致）。**若相反，全局替换即可，不影响方案结构**。【待确认-1】

## 3 原理

**一句话**：把编辑器已有的「删除命令类」直接搬进 `BlueprintViewer` 的方法体，方法只负责「参数校验 → 目标解析 → 清选中 → 构造命令 → 执行 → 通知重建 → 组装返回」，删除算法、index 重排、交叉引用维护全部由现成命令承担。

| 环节                             | 复用的既有能力                                               | 依据            |
| -------------------------------- | ------------------------------------------------------------ | --------------- |
| 删除 + index 重排 + 交叉引用维护 | `RemoveBuildingsCommand.do(data)`（`do` 只用 `data`，不碰 `updater`，见 `src/blueprint/removeBuilding.ts:43-72`） | CODE_WIKI §6.4  |
| 按 itemId 收集目标               | 等价于 `RemoveBuildingsByItemCommand` 的遍历 `itemId` 匹配（`removeBuilding.ts:114-121`） | CODE_WIKI §6.4  |
| 删除后重建                       | `RenderCore.notifyDataChanged()` → `rebuildScene("data")`（`src/lib/core/RenderCore.ts:392-395`，原子：失败保留旧场景） | CODE_WIKI §6.15 |
| 清除选中                         | `RenderCore.clearSelection()`（`RenderCore.ts:764`）        | 本次新增结论    |
| 返回结构                         | 既有 `ViewerQueryResult<T>`（`src/lib/types.ts:225-227`）    | lib-README §5.4 |
| 错误去重上报                     | 既有 `reportError` → `onError` 通道（`BlueprintViewer.ts:824-835`） | lib-README §5.3 |

**为什么不搬运 `CommandQueue`**：它用 Vue `ref` 与 `EventDispatcher.onMounted`（Vue 生命周期，`src/command.ts:5-23`、`:69-74`），搬进 lib 会破坏「Viewer 不依赖 Vue」的定位（CODE_WIKI §3 特点 5、§6.2）。本次只 `import` 命令类，不 import 队列。

**为什么 ID 模式需要映射**：命令内部以 `b.index` 与数组位置互换计算（`removeBuilding.ts:43-71`），而 R3 要求按建筑 ID 表达；且文档明确提醒 `index` 与数组下标概念不同、按区域分组不保证顺序（lib-README §8.2 第 4 条）。故先建 `Map<建筑ID, 数组下标>` 再反查位置，把"概念 ID"翻译成命令能吃的"位置"。

**【已核实】命令的隐含不变量在真实数据上成立**：`do()` 假定 `b.index === 数组下标`。对 `tests/unit/blueprint/fixtures/*.txt` 全部 8 个 fixture 实测，`indexMismatch` 均为 0（含 502 栋的 `starting_base_01029.txt`、438 栋的 `dense_splitters_v1.txt`），因此走 `b.index → 位置` 映射是安全的。该不变量一旦被外部改坏，命令会静默错乱——这属于既有约束，本方案不引入新风险，但列入 §6.5 P7 的文档告警。

## 5 工作流程

### 5.1 正常路径（文字）

1. MES和UMD 调用 `viewer.deleteBuilding(mode, targets)`。
2. **前置守卫**：`guard()`（`BlueprintViewer.ts:738-751`）覆盖「已销毁」与「初始化失败」两类；再判 `data === null || core === null` → `not-loaded`。
3. **参数校验**：`mode ∈ {0,1}`；`targets` 是数组且 `length ≥ 1`；元素为非负整数。任一失败 → `invalid-argument`。
4. **目标解析**（此阶段**只读**，任何失败都在命令执行前返回，天然满足"数据零变更"）：
   - `mode=0`：单遍遍历 `buildings`，收集 `itemId ∈ targets` 的下标，同时记录命中的 itemId 集合；`命中集合 ≠ 请求集合` → `building-not-found`（整批）。
   - `mode=1`：单遍建 `Map<建筑ID, 数组下标>`；逐个解析 `targets`，重复 ID 去重；任一未命中 → `building-not-found`（整批）。
5. **清选中**：`core.clearSelection()`。必须在重建之前——`replaceBundle` 会把 `selectedIndexesState` 原样重新套用（`RenderCore.ts:1016-1017`），而删除后下标已重排，不清就会把高亮贴到另一栋建筑上。
6. **执行**：`new RemoveBuildingsCommand(indices, data)` → `cmd.do(data)`。
7. **通知重建**：`core.notifyDataChanged()`，包 `try/catch`。成功 → `{ ok: true }`；抛错 → `build-failed`，且**必须在 message 中声明"数据已变更"**（见 §6.5 P4）。
8. **返回**：`{ ok: true, value: { mode, removed: n, indexes } }`。

### 5.2 流程表

| 步骤 | 输入          | 动作                        | 失败出口                                | 数据状态 |
| ---- | ------------- | --------------------------- | --------------------------------------- | -------- |
| S0   | 调用          | `guard()` + `data/core` 判空 | `already-disposed` / 初始化错误 / `not-loaded` | 不变     |
| S1   | mode, targets | 参数校验                    | `invalid-argument`                      | 不变     |
| S2a  | mode=0        | 收集 itemId 匹配下标 + 命中集合 | 请求集合未全命中 → `building-not-found`（整批） | 不变     |
| S2b  | mode=1        | 建 ID→下标 Map，逐个解析    | 任一缺失 → `building-not-found`（整批） | 不变     |
| S3   | —             | `clearSelection()`          | —（无返回）                             | 不变     |
| S4   | indices       | 构造并执行命令              | 命令抛错 → `build-failed`（**不做 undo**，见 P5） | 见 §6.5 |
| S5   | —             | `notifyDataChanged()`（包 try/catch） | 重建抛错 → `build-failed`（数据已变）  | 已变     |
| S6   | —             | 组装返回值                  | —                                       | 已变     |

### 6.4 核心代码骨架（已按实际签名书写）

```ts
// src/lib/BlueprintViewer.ts（新增 import）
import { RemoveBuildingsCommand } from "@/blueprint/removeBuilding";
import type { DeleteMode, DeleteOutcome } from "./types";

// 公开方法
deleteBuilding(mode: DeleteMode, targets: number[]): DeleteOutcome {
    // ---- S0 守卫 ----
    const guard = this.guard();                      // already-disposed / 初始化错误
    if (guard !== null) return guard;
    const data = this.data;
    const core = this.core;
    if (data === null || core === null)
        return this.failLocate("not-loaded", "尚未加载蓝图");

    // ---- S1 参数校验 ----
    if (mode !== 0 && mode !== 1)
        return this.failLocate("invalid-argument", "mode 必须为 0 或 1");
    if (!Array.isArray(targets) || targets.length === 0)
        return this.failLocate("invalid-argument", "targets 不能为空数组");
    for (const t of targets) {
        if (typeof t !== "number" || !Number.isInteger(t) || t < 0)
            return this.failLocate("invalid-argument", "targets 元素必须为非负整数");
    }

    // ---- S2 目标解析（只读；R5 整批失败在此落地）----
    let indices: number[];
    if (mode === 0) {
        const wanted = new Set(targets);              // itemId 请求集合（含去重）
        const matched = new Set<number>();
        indices = [];
        for (let i = 0; i < data.buildings.length; i++) {
            const itemId = data.buildings[i].itemId;
            if (!wanted.has(itemId)) continue;
            matched.add(itemId);
            indices.push(i);
        }
        if (matched.size !== wanted.size) {
            const missing = [...wanted].filter((id) => !matched.has(id));
            return this.failLocate(
                "building-not-found",
                `以下 itemId 没有任何建筑：${missing.join(",")}`
            );
        }
    } else {
        const posById = new Map<number, number>();    // 建筑ID → 数组下标，O(n)
        for (let i = 0; i < data.buildings.length; i++)
            posById.set(data.buildings[i].index, i);
        const seen = new Set<number>();
        indices = [];
        for (const id of targets) {
            if (seen.has(id)) continue;               // 重复 ID 去重【待确认-2】
            const pos = posById.get(id);
            if (pos === undefined)
                return this.failLocate("building-not-found", `建筑 ID ${id} 不存在`);
            seen.add(id);
            indices.push(pos);
        }
        indices.sort((a, b) => a - b);
    }

    // ---- S3 清选中（重建会重新套用旧下标，必须先清）----
    core.clearSelection();

    // ---- S4 执行（命令自带 index 重排 + 交叉引用维护）----
    try {
        const cmd = new RemoveBuildingsCommand(indices, data);
        cmd.do(data);
    } catch (e) {
        // 理论不达；若达说明数据本身已不自洽（如 b.index 与数组位置不符）
        // 不做 undo：do 未完整执行时其内部状态不足以支撑回滚
        return this.failLocate(
            "build-failed",
            `删除命令执行失败（数据可能已部分变更，建议重新 loadBlueprint）：${String(e)}`
        );
    }

    // ---- S5 通知重建（原子：失败保留旧场景，但数据已变）----
    try {
        core.notifyDataChanged();
    } catch (e) {
        return this.failLocate(
            "build-failed",
            `已删除 ${indices.length} 栋但场景重建失败（数据已变更，请重新 loadBlueprint）：${String(e)}`
        );
    }

    // ---- S6 返回 ----
    return { ok: true, value: { mode, removed: indices.length, indexes: indices } };
}
```

要点说明：

- `failLocate(code, message)` 的真实签名见 `src/lib/BlueprintViewer.ts:760-767`，返回 `{ ok: false; error: ViewerError }`，与 `DeleteOutcome` 兼容；rev.1 的三参数 `fail(...)` **不存在**（实际 `fail` 只收 `ViewerError`，见 `:753-757`）。
- `core.clearSelection()` 放在解析之后、执行之前：解析失败时选中态不应被无谓清空。
- 两个 `try/catch` 是分开的：命令阶段失败时数据**可能**被部分改动，重建阶段失败时数据**确定**已改动，两者的 message 必须区分，宿主据此决定是否重新加载。

### 6.5 安全要点（必须逐条满足）

| 编号 | 要点           | 实现约束 / 核实结论                                          |
| ---- | -------------- | ------------------------------------------------------------ |
| P1   | **不引入 Vue** | 【已核实】`removeBuilding.ts:2` 的 `import { Command } from "@/command"` 是纯类型引用，TS 5.3.3 编译时会被整体擦除（`transpileModule` 实测输出无该 import）；本次实跑产物 `vue` / `onMounted` / `CommandQueue` 命中均为 0。**仍需加一道守卫**：eslint `no-restricted-imports` 禁止 `src/lib/**` import `@/command`，防止后续误引值成员 |
| P2   | **发布面收窄** | `index.ts` 只加 3 个类型导出，不加命令类、不加 Updater        |
| P3   | **不抛异常**   | 全部失败路径走 `failLocate()`；两处 `try/catch` 分别兜命令与重建 |
| P4   | **原子性**     | 整批失败发生在命令执行**之前**（S2 只读）；执行阶段是同步纯内存操作，无 IO、无 await。**唯一例外**：S5 重建抛错时数据已变，必须用 `build-failed` + "数据已变更"文案告知宿主 |
| P5   | **回滚**       | 解析阶段零变更即天然回滚。命令 `do()` 抛错时**不要**调 `cmd.undo(data)`：`undo` 依赖 `do` 完整跑完才建立的内部状态（`removed` / `dangling` / `oldIndexOfNew`），半途失败后回滚只会二次破坏。改为返回 `build-failed` 并在文档建议 `loadBlueprint` |
| P6   | **性能**       | 【已核实】命令本体不是瓶颈：n=30000 实测 k=100/1000/5000/10000/20000 → 35/23/37/45/50 ms，最坏分布（分散下标、k=5000）92 ms。**不设栋数上限**。真正的成本是每次调用触发一次全量 `rebuildScene`（3 万建筑秒级），因此文档约束改为"**尽量把目标合并进一次调用**，避免 for 循环逐栋删除" |
| P7   | **共享引用**   | 【已核实】`getBlueprintData()` 返回 `this.data` 引用本身（`BlueprintViewer.ts:275-277`），与 `core.data` 同一对象；删除会**原地改写宿主手里的旧引用**。必须在 `lib-README` 明确告警，并说明"需要快照请自行深拷贝或先 `exportBlueprintJSON()`" |
| P8   | **选中态**     | 【已核实】`notifyDataChanged()` **不清选中**（`RenderCore.ts:392-395`），而 `replaceBundle` 会把旧下标原样重新套用（`:1016-1017`，仅丢弃越界项）→ 删除后高亮会指向别的建筑。方法内必须先 `clearSelection()`（见 S3） |
| P9   | **ID 口径**    | `mode=1` 的 ID 是 `BlueprintBuilding.index`；注意与同库 `selectBuilding(index)` 的语义**不同**（后者是"数组下标优先、越界按 ID 兜底"，见 `:784-790`）。`lib-README §5.2` 必须写明差异，否则宿主必踩 |
